# Blog Voice — 本仓库中文博客腔

这套规则是从 `src/data/blog/` 里 56 篇真实文章蒸馏出来的，不是审美偏好。每条都尽量带「原句 + `文件:行`」或可复算的计数，能查就能改。

先过一遍核心：**讲我自己遇到的事，用长句带过去，数字和报错一个字不改，结尾给一句态度。**

## 语料与口径

- 语料：`src/data/blog/*.md`，56 篇（统计截至 2026-10-30）。
- 主力样本（近两年、本人原创技术帖，腔最稳）：`raycast-a-productive-tool-on-mac-which-beyond-the-alternative-of-alfred-and-spotlight.md`（2023）、`xmlabit-a-xml-node-sort-tool.md`（2021）、`openclaw-upgrade-pitfalls.md`（2026-06）、`claude-code-2-1-186-billing-pitfall.md`（2026-06）、`agent-ex-workbuddy-minimax-opencode-token-freedom.md`（2026-10）。
- 读书笔记系列（`10-minutes-learning-*`、`mindmap-*`）多为摘录和译文，**不要当腔调样本**。
- 下面所有计数都可以用 `scripts/check_voice.py --corpus` 复算；段长口径是「正文段落、去掉标题/列表/代码/引用后，去掉 markdown 记号的中文字符数」。

## 必备（每篇都要）

1. **第一人称、经历先行。** 先说我在什么处境下动了手，再说这东西是什么。功能跟着使用场景走，不先给定义再展开。
   - `openclaw-upgrade-pitfalls.md:20`「我之前在旧笔记本上装了 OpenClaw，有段时间没更新了，日常也就用来干一些杂活…」
2. **短句起头 + 逗号长句收尾。** 段落中位数落在 40–110 字（五篇主力样本的中位数：51 / 61 / 80 / 103 / 100，均值 50 / 75 / 92 / 105 / 97；五篇合并 p10=27、p50=66、p90=140）。一句话里靠逗号一路带下去，不靠破折号叠层解释。超过 180 字的段落在语料里只占 3%，命令密集的操作文能到 21%。
3. **真实值原样。** 数字、版本号、报错原文、命令、路径一字不改，不四舍五入、不换量纲。例：`7.44MB`、`2.4M tokens`、`v2.1.150`、`2026.5.18`。改稿一律用 `--base` 跟旧稿比一遍。
4. **一段一件事。** 换话题就换段，必要时加 `---` 分隔线（`openclaw-upgrade-pitfalls.md`、`claude-code-2-1-186-billing-pitfall.md` 都在换场处用）。

## 偶用（用了是加分，每样一次就够）

频率都标了，用密了立刻变成「模仿痕迹」：

- **先说结论** —— 全站只 1 次（`claude-code-source-leak.md:88`：先说结论：**这不算开源。**）。
- **「最后的最后」** —— 8/56 篇；可以是 H2，也可以是收尾段开头的半句（`claude-code-2-1-186-billing-pitfall.md:112`）。
- **「坑一/坑二…」** —— 1 篇（`openclaw-upgrade-pitfalls.md` 5 处，标题形如 `## 坑二：5.18 的 Session Lock 大坑💩💩`）。
- **`Intro` / `End` 英文锚点** —— 只有 raycast（2023）和 xmlabit 用过，别复活。
- **类比一句带过** —— 施工图纸那句（`claude-code-source-leak.md:98`），一句就停，不展开。
- **「以后再补充」** —— 1 次。
- **编号小节 `### 1. 锁版本`** —— 只给「照着做的操作步骤」用（`claude-code-2-1-186-billing-pitfall.md:114` 起 3 个），都是动词短语、不带宽句。论述分层不要编号，那是产品文档味。
- **现象 / 原因 / 修复方法 三个加粗标签** —— 只在踩坑复盘里用，独占一行、后面跟段落，一组三个就够（`openclaw-upgrade-pitfalls.md` 共 10 处，还有影响范围、结局）。

## 措辞（括号内是 56 篇里的次数/篇数）

- **自然连接词**：其实(98/38)、但是(95/39)、先(80/39)、结果(62/30)、所以(28/18)、而且(21/13)、于是(17/11)、不过(16/12)、居然(8/8)、赶紧(6/5)、果然(5/2)、正好(5/4)。
- **自嘲与吐槽**：坑(50/10)、崩溃(12/6)、踩坑(7/3)、头秃(5/4)、草台班子(2/2)、拉完了(2/1)、薅(4/1)、真香(2/2)、一坨(1)、要老命(1)、吐槽(3/2)。
- **不要用**：语料里 0 次的词，写了就是「像但不是」——白嫖、卧槽、牛逼、手动挡。`说白了` 只有 1 次（旧版 skill 把它当常用词，是错的），要表达同意思就用 `其实`。
- 吐槽要骂得具体：骂哪个功能、什么行为、哪一版，不空骂。`claude-code-2-1-186-billing-pitfall.md`「这个 gate 位置加得太故意了——专门把第三方 provider 的自动压缩功能关掉」。

## Emoji

**情绪 emoji 频次（全站）**：😂16、🤣6、🌚6、💩5、🙏5、😱4、😲4、🙂4、😮3、🤬3、😓3、🤕3。
**功能符号**：✅13（清单打勾）、⚠️10（标真实的坑）。

**系列符号**（不是情绪，是人格）：🦞6 / 🦊9 属于「养虾日记」，指 OpenClaw 助手；🌈7 是「效率工具」标题色。

**连写 = 加力**，2–6 个，只在情绪顶点（被产品坑、自己翻车、发现彩蛋）：😂😂(3)、😂😂😂(1)、🌚🌚🌚(2)、💩💩💩(1)、🤬🤬🤬(1)、😓😓😓(1)、😱😱😲😲😲😲(1)、🙂🙃🙂🙃🙂(1)、🌈🥚🌈🥚🌈🥚(1)。正经说明句里不放。

**不要用**语料外的 emoji（🚀✨🎯💡 这类「PPT emoji」），一个都不要。

**⚠️ 用法**：`⚠️ 注意全局 npm 安装路径：…` —— 只标真会伤到人的坑，不用来表示「重点」。

## 排版

- 破折号用于**一个**短补充就收：「问题出在这个 map 文件指向的路径——它指向了 Anthropic 内部的 R2 存储桶」（`claude-code-source-leak.md:80`）。一句最多一个 `——`，不叠两层。
- 列表只给可执行步骤或并列清单（装包、配置项、验收标准）；讲道理一律用段落。
- 加粗只有两种：句内关键词（`**不要升级Claude Code！**`）和短标签独占行（`**现象：**`）。
- **独占行加粗必须是 ≤8 字 + 冒号 的标签**（现象/原因/修复方法/影响范围/结局/目标/现状/约束/验收），连着最多 2–3 个。把论点句写成独占行加粗、再排成一串，就是最典型的 AI 腔，见下节。

## frontmatter

标题和描述也算这个腔，agent 写博客必然要写它们：

- `title`：`主标题｜副标题`（全角竖线）或单句。系列文前缀一个符号：`🦞养虾日记｜…`、`🌈效率工具｜…`、`🧠 穷鬼 AI 工作流｜…`；带情绪的写法也常见：`踩坑记录｜被 A 畜 Claude Code 气到心塞`。
- `description`：一句话讲清「这篇踩了什么坑 / 解决了什么」，可以是同腔的口语判断（`openclaw-upgrade-pitfalls.md`「…这些坑我都替你踩过了」），不要写成摘要腔。老文常见 `description` 直接等于 `title`，照抄也行。
- `pubDatetime` 用 UTC（`Z` 结尾）；`tags` / `categories` 沿用现有系列（养虾日记、踩坑记录、技术笔记、随笔…），不新造。

## 禁止的 AI 腔（只列博客特有的）

通用空话、模板句式、确定性漂移这些**不在这里重复**——那份清单在 humanizer-zh，两边各写一份必然漂移。这里只管博客特有的：

- 每节总-分-总、先定义再举例的产品文档结构。
- 排比式加粗小标题（每段以「**把任务派出去。**」开头那种列点）。
- 纯拔高式的「不是 X，而是 Y」对比（语料里没有这种句式：`不是` 86 次全部是正常否定，没有一次是假对比）。
- 赋能、抓手、综上所述当形容词/套话用（均 0 次）。`闭环` 只在 `agent-ex-workbuddy-minimax-opencode-token-freedom.md:68`「最小闭环五步」出现过一次，是技术名词，别拿去当「打通闭环」用。
- 抽象结论后面不补场景，直接跳下一条。
- 对着「读者/用户」做产品说明的口吻。这里是给朋友讲我干了什么。

## 改写手法

1. 先去掉加粗标题层，把列点熔回叙述段。
2. 每个抽象结论后面要有「我」的具体场景（哪个窗口、什么时间、报了什么错）。
3. **要不到真实场景就问作者，宁缺不编。** 编经历、编数字、编报错，违反 humanizer-zh 第 1 条优先级（不新增原文未提供的事实、经历、数字），单独用本 skill 时尤其容易犯。实在拿不到就删掉这句抽象结论，或留 `<!-- TODO(作者): 这里缺一个具体场景 -->`，不要用「比如有一次…」现编。
4. 长句拆不拆看呼吸感：短句起头、逗号长句收尾，不追求句句齐整。

## 对照示例

**A. 真实原文，照这个感觉写**（`agent-ex-workbuddy-minimax-opencode-token-freedom.md:28`）：

> 我作为两个 agent 工具中的“接线人”，两边传话实在有点累，于是，就有了这个“穷鬼工作流”——`agent-ex`。

**B. 反例 vs 自拟改写（改写稿不是原文，别当语料抄）**

改前（AI 腔）：

> 本质就一件事：让主 agent 能驱动外部的 agent 干活，而且这个活不是派一次就断，是可以来回转的协作。具体拆成四件：**把任务派出去。**……

改后（自拟，仅示意节奏，非原文）：

> 其实这件事就一个目的，让主 agent 能把活派给外面的 agent，派出去不是一次就完，中间还能来回转。我原来在两个窗口之间来回传话，现在这活交给它了。

## 与 humanizer-zh 的边界

| | 管什么 |
|---|---|
| humanizer-zh | 通用去空话、去模板、保留事实与确定程度、**不新增经历和数字** |
| blog-voice | 只用本仓库语料定「腔」：段落节奏、emoji、结构锚点、标题与描述写法、结尾收法 |

- 改稿顺序：先 humanizer-zh 去 AI 味，再按本 skill 调腔。
- 新写：直接按本 skill 写，交付前用 humanizer-zh 第 1 条自查（有没有编事实）。
- 冲突时 humanizer-zh 第 1 条优先。

## 交付前自检

**机器能查的**（只报告不修改）：

```bash
python3 .agents/skills/blog-voice/scripts/check_voice.py src/data/blog/<新文>.md --base <旧稿>
python3 .agents/skills/blog-voice/scripts/check_voice.py --corpus   # 复算本文所有统计
```

判据（阈值是按 56 篇语料反推的，现有 56 篇全部通过，不会冤枉本人写法）：

| 检查 | 判 |
|---|---|
| frontmatter `title` / `description` / `pubDatetime` | 缺一个就 FAIL |
| 段落中位数 40–110 | 越界只 warn |
| >180 字的段落占比 | >25% FAIL（语料中位 3%） |
| 短句口号独占行加粗（`**把任务派出去。**` 这种） | ≥3 处 FAIL，1–2 处 warn |
| 语料外的 emoji、连写超 6 个 | FAIL |
| 语料 0 次的词（白嫖/卧槽/牛逼/综上所述/赋能…） | FAIL |
| `--base` 下数字、行内代码被改动或消失 | FAIL；新增数字 warn |

**机器查不了的，人工四项**：

- [ ] 开头是「我先遇到什么」，不是「X 是什么」。
- [ ] 每段只讲一件事；抽象结论后面有具体场景，且场景是真的。
- [ ] 数字、报错、命令与原始记录逐字一致。
- [ ] 结尾 1–2 句带态度。常见收法：情绪/自嘲（`openclaw-upgrade-pitfalls.md` 结尾「这世界就是个巨大的草台班子。🤕🤕🤕」）、祝愿号召（raycast「祝大家五一快乐！🤗」/「欢迎Star和PR」）、反思一句（agent-ex「桥只是让人少跑几趟腿，路还是自己走。」）、签名（`**吴小黑♠️ with 尾酱🦊 ✨**`）。纯操作收尾的文章（`claude-code-2-1-186-billing-pitfall.md`）把态度放在「最后」小节，末尾自然收在步骤上，不用硬加 emoji——全站末段带 emoji 的只有 3/56 篇。
